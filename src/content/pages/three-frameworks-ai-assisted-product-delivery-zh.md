## 为什么产品经理需要新的工作方法

AI 编码智能体正在改变产品的构建方式。Claude Code、Cursor 等工具让产品经理可以制作原型、整理交接材料并验证工作流程，不一定要等到一个开发周期结束。但如果只是输入提示词、拿到输出后就结束，很难判断结果是否可靠或将经验用于下一次工作。

我用三个视角让这类工作更有结构：Harness Engineering 和 Vibe Coding 已在业界使用；Loop Engineering 是我用于思考持续迭代的个人工作概念。下面是我从产品交付角度对它们的理解。

## 1. Harness Engineering：设计智能体工作的环境

模型负责生成，智能体循环决定下一步做什么，而 harness 是智能体周围的工作环境，它会影响产出是否可用、可检查。

我会关注五个方面：

- **上下文：** 智能体能看到什么？包括项目结构、约定、领域知识和具体任务。
- **工具：** 智能体可以做什么？例如读写文件、调用 API 或运行测试；每项能力也伴随风险。
- **约束：** 智能体不能做什么？例如范围限制、安全规则和风格规范。
- **测试与反馈：** 如何判断任务是否完成？可以使用 lint、类型检查、测试和人工审查。
- **状态与交接：** 信息如何跨会话保留？例如 CLAUDE.md、结构化文档和 Git 历史。

产品经理的工作是判断哪些上下文重要、限定工具使用范围、设置产品层面的护栏并编写验收标准。工程师负责实现层面的细节。这是一项需要共同完成的工作。

## 2. Loop Engineering：设计如何持续改进

一次性提示通常得到初稿，产品则需要经过审查和迭代。我用 Loop Engineering 描述如何设计反馈循环，让每轮工作的发现能够进入下一轮。

我会区分五种循环：

- **产品循环：** 想法、问题定义、原型、评估、反馈、更新上下文，再进入下一轮。
- **实现循环：** 生成代码、测试、审查、修复和提交。
- **评估循环：** 指标、测量、分析和调整。
- **用户反馈循环：** 使用、观察、洞察和产品更新。
- **上下文更新循环：** 总结经验、更新文档，改善下一次工作。

关键是让结果能够传递到下一轮。缺少共享记录时，经验可能丢失；循环无法闭合时，团队也可能重复已经发现过的问题。

## 3. 用 Vibe Coding 探索产品

在我的工作语境中，Vibe Coding 指产品经理主导、借助编码智能体制作原型，以探索产品想法。这里的重点是用可运行原型学习，而不是直接交付生产代码。

它适合需要看到工作界面的早期想法、编写详细需求前的流程验证、通过可点击原型与利益相关者沟通，以及投入工程资源前的初步可行性探索。

原型不能代替生产工程、架构决策、安全审查或扩展性验证。探索的价值在于得到什么认识，而不只是留下多少代码。

提示词之外，重要的是定义产品：用户问题是什么、主要流程如何运行、数据模型是什么，以及原型达到什么程度就足以验证当前问题。

## 三者如何连接

这三个视角关注不同层面：

- **Harness Engineering** 关注智能体工作的环境。
- **Loop Engineering** 关注反馈如何让环境与产品工作持续演化。
- **Vibe Coding** 是可以从两者中受益的一种具体应用，例如制作探索性原型。

我会用相同的问题贯穿三者：智能体需要什么上下文？怎样算一次失败？原型让我们对用户的真实任务有了什么认识？交接文档的价值在于让这些答案可供审查，而不只是套用模板。

## 从哪里开始

如果你是与 AI 编码智能体协作的产品经理，可以试试：

1. 为项目写一份 CLAUDE.md，记录必要的约定和上下文。
2. 给出清楚的验收标准，借助编码智能体制作一个产品想法的原型。
3. 在原型完成后记录收获，并更新下一轮所需的项目上下文。

这些视角是实践工具，用来帮助我们更有结构地协作，让结果更容易复用和审查。
