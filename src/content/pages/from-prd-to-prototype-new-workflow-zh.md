## 传统 PRD 的问题

传统 PRD 描述要构建什么。在 AI 产品工作中，“做什么”很大程度取决于模型能够做到什么，而这种能力变化很快。工程团队读完静态 PRD 之前，其中一些假设可能就已过时。

## 一种不同的工作流

我开始使用三步循环，而不是写完 PRD 就直接交接：

### 1. 先定义本体

在写需求之前，先梳理领域：有哪些实体？哪些关系重要？可以执行哪些操作？这会成为产品经理、工程师和 AI 系统之间的共同语言。

### 2. 用 Vibe Coding 构建原型

使用 Claude Code 或 Cursor 构建能展示核心流程的可运行原型。它不只是界面稿，还用于验证数据流、智能体逻辑和用户交互方式。

### 3. 与工程团队一起迭代

带着原型和本体参加工程评审。大家不再只围绕抽象需求讨论，而是可以对照可运行的系统和具体数据模型。

## 为什么这样做

原型让需求变得具体，本体让领域结构变得清晰。两者可以帮助团队更早发现歧义，而不能替代工程验证。

[Prompt-to-Ontology](/zh/projects/prompt-to-ontology/) 的构建也遵循了这条思路：先梳理本体，再通过 Vibe Coding 制作原型并迭代。
